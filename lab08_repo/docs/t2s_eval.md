# Результат 4. Оцінка text-to-SPARQL

## 1. Конвеєр

`промпт зі схемою` → **LLM** → `парсер` (витяг SPARQL з відповіді, `scripts/t2s.py: extract_sparql`) → `перевірка синтаксису` (rdflib `prepareQuery`) → `перевірка схеми` (усі IRI простору `dkh:` мають існувати в TBox/ABox; сторонні IRI, окрім rdf/rdfs/owl/xsd, заборонені) → `виконання з LIMIT 200` для SELECT без власного LIMIT (pyoxigraph) → `порівняння з еталонною відповіддю` (таблиці порівнюються як множини рядків, незалежно від імен змінних і порядку; числа — за значенням).

**Хто був «LLM».** Генератори запитів — окремі субагенти тієї самої моделі (налаштована `claude-sonnet-5-5`; фактична може відрізнятися), які бачили лише вхідний файл промпту (`llm_log/in/`) без еталонів і без доступу до коду перевірки. Температуру й seed контролювати неможливо — це обмеження; результат повторного запуску може відрізнятися. Ключів API та персональних даних немає (дані синтетичні).

## 2. Тестовий набір

`tests/t2s.jsonl`: 24 питання (18 **dev** + 6 **held-out**), поля `id, split, question, gold_query, gold_answer`. Еталонна відповідь обчислена виконанням еталонного запиту (`scripts/build_t2s.py`); еталонні запити та відповіді склала та сама система (Claude), а не незалежний експерт — це суттєве обмеження. Вручну (за `abox.ttl`) перевірено: d08 (Sofiia — 17 років), d09 (Iryna, Petro), d10 (Halyna, Iryna), d11 (є VAR-001, VAR-103 з Pathogenic).

Типи: пошук за властивістю, FILTER, COUNT/MAX/AVG, GROUP BY, HAVING, ASK, property path (`+`), `FILTER NOT EXISTS`, запит до TBox.

**Щоб уникнути «підгонки під тест»:** v2 писалась лише за помилками v1 на dev-питаннях; held-out питання (h01–h06) у цьому аналізі не розглядались. Але два приклади в v2 мають ті самі візерунки, що й класи помилок (анотація за іменем), тож dev-метрика v2 завищена; довіряти слід held-out, а їх лише 6.

## 3. Промпти

- v1 (`llm_log/prompts/v1.txt`): опис задачі + автоматично згенерована схема (79 класів, 53 властивості з domain/range) + питання.
- v2 (`llm_log/prompts/v2.txt`): те саме + 7 правил моделювання (з аналізу помилок v1) + 2 приклади поза тестовим набором.

Перші дві метрики однакові (100%) в обох версіях: схема входила в обидва промпти, тому модель не вигадувала IRI. Це не доводить, що перевірка схеми «працює», тому вона перевірена окремо в `tests/test_t2s.py` на навмисно хибному запиті (`dkh:hasQD` → відхилено). Вирішальна метрика — правильний результат: 16 → 18 з 24 (67% → 75%), на dev 12 → 14, на held-out 4 → 4. Різниця в 2 питання на вибірці з 24 є в межах шуму повторного запуску (температуру не контролювали), тож **покращення не можна вважати встановленим**.

Зміни по питаннях: v2 виправила d02, d04, d11, d12, d14, d17 (dev) і h04 (held-out) — 7 питань; зламала d03, d08, d09, d10 (dev) і h01 (held-out) — 5 питань (клас E6).

## 5. Класифікація помилок

| Клас | Опис | Реакція |
|---|---|---|
| E1 | Немає виведення: вузли добираються через надклас (`a dkh:GeneticVariant`, `a dkh:QualityAnnotation`), а в сховищі ці типи є лише для частини вузлів | промпт: правило 2 (спиратися на властивості) |
| E2 | Клінічна значущість — індивід без `rdfs:label`, а модель шукає її за міткою «Pathogenic» | промпт: правило 4 (порівнювати IRI) |
| E3 | Немає `DISTINCT`: дані в кількох іменованих графах → дублікати (200, 200, 60, 60) | промпт: правило 5 |
| E4 | Зайвий стовпець у відповіді (`?v` разом з `?id`); результат за змістом правильний, але метрика порівнює таблиці суворо | промпт: правило 6; частково вада самої метрики |
| E5 | Шанс успадкування записано в TBox як OWL-обмеження (`owl:onProperty/owl:hasValue`), а модель шукає пряму властивість у класу — із промпту цього не випливає | не виправлено: на dev-питаннях такого класу немає, тож правило в промпт не додавалось (щоб не підглядати у held-out) |
| E6 | **Нова помилка, внесена v2**: правило 7 («мітки мають вигляд rdfs:label») підштовхнуло до пошуку особи за міткою `"Olena"`, а мітки в графі мають мовний тег (`"Olena"@en`), тому літерал без тегу не збігається | не виправлено у цій роботі; потрібна v3: шукати іменованих осіб/гени за IRI (`dkh:Olena`) |

### Приклад: E6 (v2, d09)

Питання: «Хто є батьками Olena?»

```sparql
SELECT DISTINCT ?label WHERE { ?c rdfs:label "Olena" ; dkh:hasParent ?p . ?p rdfs:label ?label }
```

Еталон: `dkh:Olena dkh:hasParent ?p . ?p rdfs:label ?l`. Запит моделі порожній, бо `rdfs:label` в `Olena` — це `"Olena"@en`.

## 6. Верифікація

- Парсер і перевірка схеми — рівень **V2** (автотести `tests/test_t2s.py`, у т. ч. на негативних прикладах).
- Метрики на 24 питаннях обчислені скриптом `scripts/eval_t2s.py` і відтворювані з `llm_log/raw/`. Вимога V4 («незалежна перевірка») **не виконана**: еталони склала та сама система, що й генератор; я ставлю цим метрикам V2/V3-, а не V4.
- Сирі відповіді моделі: `llm_log/raw/v{1,2}_b{1,2}.json`; розбір кожної відповіді: `llm_log/eval_v{1,2}.json`.

## 7. Обмеження і що далі

- 24 питання, 6 held-out; один прогін кожної версії; temperature/seed невідомі.
- Синтетичний малий граф; питання складені після онтології, тобто модель і питання «знайомі» зі схемою.
- Метрика порівняння сувора до проєкції стовпців (E4).
- Наступний крок: v3 без правила 7 (іменовані сутності — за IRI) та повторні прогони кожної версії (≥3), щоб оцінити розкид.
