# Agent evaluation (lab 15, R3)

Generated by `python scripts/make_eval.py`. Raw results: `eval/v0.json`, `eval/v1.json`, `eval/v2.json`; traces: `logs/trace_v0.jsonl`, `trace_v1.jsonl`, `trace_v2.jsonl`; metrics: `eval/metrics.json`.

## 1. Set-up and honest scope

* **Scenarios:** `tests/agent_scenarios.jsonl`, 25 scenarios = 13 success, 6 "don't know" (3 required), 6 source conflict (2 required). Each has the role, the expected tool(s), expected status and answer criteria (`must_include` = list of alternatives that must all be present, `forbid`, `expected_status`).
* **Agent brain:** no API key was available. The LLM calls of the agent (planner, drafter) were produced offline by blind `claude-haiku-4-5` sub-agent runs that saw only the prompt; outputs were stored in a replay cache (`llm_cache/`, protocol in `llm_log/`). Temperature/seed could not be set → results are one sample, not an average. Tools, retrieval, SQL, graph and verifier are real code executed on the real data.
* **Memory is off** in all runs (planner `MEMORY: none`): the episodic hint would change the prompts and invalidate the replay cache; the memory module is unit-tested only.
* **Judging:** automatic (status + answer substrings + citation validity + expected tool called). Automatic criteria are crude; I also read all answers (V1/V2 by the author's assistant — a second LLM role, **not** a human domain expert, so V3 is pending).
* **Three versions:** `v0` = the first code state, run only on the first 16 scenarios; `v1` = after the validator bug fix (F1), all 25 scenarios (the 9 scenarios `H01–H09` were added after the first run to get harder cases — this is test-set growth *after* seeing results, so v0→v1 is not a clean held-out comparison); `v2` = planner/drafter prompts v2 + verifier fix (F2, F3). H02's criterion was strengthened after manual reading (see F3), so v1 is re-judged with the final criteria.
* **Cost is modelled**, not billed: tokens are estimated (≈4 chars/token Latin, ≈2.5 Cyrillic) and priced at an assumed $1 / $5 per million input/output tokens (unverified).

## 4. Failure analysis and fixes (R3 C3)

### F1 — read-only validator rewrote string literals (4 of 16 scenarios failed in v0)

* **Symptom:** S01, S05, S07, S08 answered NO_ANSWER or "0 variants" although the data exist. Example v0 answer to S01: «У хабі немає (доступної) інформації про гени, що входять до панелі HBOC-panel: запит до графа [graph#1] не повернув жодного рядка.».
* **Root cause (read from the trace):** the planner's Cypher was correct (`MATCH (p:GenePanel {name: 'HBOC-panel'})…`), but `validate_cypher` returned the *comment-stripped copy* used for keyword checks (string literals replaced by `''`), so the executed query matched `name: ''` and returned 0 rows; the drafter then honestly (and correctly given its evidence) said there was no information. A tool bug, not a model error — the citation verifier cannot catch it because the answer is faithful to a wrong observation.
* **Fix:** the validator now checks the stripped copy but returns the original statement with only LIMIT normalised (`agent/guards.py`); regression tests `test_literals_are_preserved`, `test_string_literal_with_keyword_is_not_a_write`.
* **Result:** S01, S05, S07, S08 → ✓ in v1/v2 (v0 4/8 → 8/8 on success scenarios of the original set).

### F2 — verifier rejected correct derived numbers (3 of 25 scenarios in v1)

* **Symptom:** H01, H03, H09 ("compare / what is the difference") triggered a redraft: the verifier reported «numbers not found in the observations: 0.6 / 24 / 0.2». v1 cost: +2 steps each (6 instead of 4), a repeated LLM call, and the second draft was still identical, so the warning stayed in the log.
* **Root cause:** the grounding check accepted only numbers literally present in the observations; differences are legitimately derived. (A second, smaller bug found while fixing it: the number regex read the CSV row `2025,10012` as one number, hiding 10012 from the arithmetic — fixed together.)
* **Fix:** `ungrounded_numbers(..., derived=True)` accepts differences and sums of pairs of observed numbers; draft prompt v2 asks the model to show the arithmetic with the observed numbers.
* **Result:** redrafts 3 → 0; H01/H03/H09 now need 4 steps and pass without verifier warnings. Trade-off: a made-up number that happens to equal a difference of two observed numbers would now pass (residual risk, see `docs/agent_security.md`).

### F3 — planner's query did not return the evidence for the relation (H02)

* **Symptom:** question «Які порогові значення FS використовує процедура HF-01 для SNP та INDEL?». The v1 planner anchored the query on HF-01 but returned only `t.variantType, t.op, t.value`, so the observation did not show the Procedure→Threshold link; the drafter correctly hedged: «Результат запиту містить пороги для двох типів варіантів: для SNP — > 60.0, для INDEL — > 200.0 [graph#1]. Однак спостереження не називає процедуру HF-01 і не зазначає, що ці значення є фільтрами FS, тож зв'язок із HF-01 не підтверджено [graph#1].». Auto-criteria first passed it (60 and 200 present); manual reading showed that the answer did not state the HF-01 link → I strengthened the criterion (`must_include` HF-01, `forbid` hedging phrases) and re-judged v1 → ✗.
* **Root cause:** plan prompt v1 did not require the query to return the properties that prove the relation (e.g. `p.id` next to the threshold), so the evidence shown to the drafter could not support the claim that these thresholds belong to HF-01.
* **Fix:** plan prompt v2 adds an ANCHOR rule (start the Cypher from the named entity and return the properties that prove the relation) and a CONFLICTS rule (always call `get_claims` for threshold/version questions).
* **Result:** v2 answer: «Процедура HF-01 використовує для SNP поріг FS > 60.0 [graph#2], а для INDEL поріг FS > 200.0 [graph#2]. Альтернативний локальний поріг FS > 45.0 [CF-FS:local] у наданих даних не пов'язаний із HF-01 і має статус alternative; рішення очікує затвердження людиною » — ✓. Side effect: the CONFLICTS rule adds a `get_claims`/`search_docs` call to threshold questions (mean tool calls 0.84 → 1.12, cost +8%).

## 5. Re-run and improvement (R3 C4)

All 25 scenarios re-run on v2 with the same replay protocol: success 96% → 100% (v1→v2), v0 on the first 16: 75% (the same 16 under v2: 16/16). Mean steps 4.08 → 4.12; redrafts 3 → 0; mean modelled cost per query 0.00247 → 0.00267 USD (slightly higher: more tool calls).

**What this does and does not show.** The improvement is real for the three analysed failures and is reproducible from the replay cache (`bash scripts/run_all.sh`), but: n = 25 on one author's scenarios; one LLM sample per prompt; the scenario set grew after seeing v0; a 100% on 25 easy-to-medium scenarios is not evidence that the agent is reliable on the long tail. The unknown/conflict scenarios were passed already by v0/v1 — they mainly test the refusal and the register tool, not subtle model failures.

## 6. Conflict and "don't know" behaviour

* Conflicts (C01–C04, H04, H08): the agent lists each value with source id, scope and status, marks the register's *active* claim and states that the decision is pending human approval (V3) — it does not pick a winner on its own. H04 (user premise «Java 1.8») is corrected: 1.8 is a superseded/outdated claim, current is 17.
* "Don't know" (U01–U04, H05, H06): no tool needed or role denied; answers are NO_ANSWER without restricted values (U02, H05 use the role scope). U03 still spent one `graph_query` (a wasted step) before answering NO_ANSWER.
