# Agent specification — Domain Knowledge Hub agent (lab 15, R1)

Generated by `python scripts/make_spec.py` from `agent/tools.py` (tool schemas) and `agent/config.py` (limits). Status: **draft written with LLM assistance; owner review (student) pending**.

## 1. Goal, users, boundaries

**Goal.** Answer questions about the Hub (medical genomics: variant-calling documentation, the knowledge graph, the DuckDB warehouse with a semantic layer, the register of conflicting claims) *only from retrieved evidence*, with citations to source ids, and say "no answer" when the evidence is missing or the caller is not allowed to see it. The agent never decides clinical actions.

| User (role) | What they may ask | Data they may see |
|---|---|---|
| `reader` | documentation, public graph facts (genes, panels, procedures, thresholds), warehouse metrics, claim register | `public` chunks; graph labels without Person/Diagnosis/Variant/Annotation/Sample |
| `analyst` | + internal notes, variants, annotations, samples | + `internal` chunks, labels Variant/Annotation/Sample |
| `clinician` | + patient-level facts (Person, Diagnosis) | + `restricted` chunks, labels Person/Diagnosis |

The role is set by the deployment (API session / MCP server env `DKH_ROLE`), never by the content of a message or a tool result.

**Out of scope (the agent answers "no information"):** medical advice or dosing, prognosis for a person, data that is not in the Hub (prices, other domains), requests to change its own rules, writing to the Hub other than through `propose_fact`.

**Autonomy levels.**

| Level | Actions | Who decides |
|---|---|---|
| L0 read | `search_docs`, `graph_query`, `sql_metric`, `get_claims` (all read-only, within limits) | agent, automatically |
| L1 propose | `propose_fact` creates a *proposal* (validated, risk-classified); low risk may be auto-accepted into the staging register, nothing is merged into the Hub | agent + validator |
| L2 approve | medium/high-risk proposals wait for a human; only the human decision writes (with provenance) | human (Hub owner) |
| L3 | not available: schema changes, deletions, role/permission changes, access to restricted data beyond the caller's role | nobody through the agent |

## 2. Tools (R1 C1)

Five tools; schemas are JSON Schema (draft 2020-12 subset). `propose_fact` is not offered to the planner; it is available through the MCP server and the HITL flow (`docs/hitl.md`).

### `search_docs`

Hybrid (BM25 + dense) search with reranking over the documentation corpus (GATK/Sarek/bcftools manuals, lab notes). Returns up to k text chunks with ids to cite. Read-only. Only chunks whose sensitivity is allowed for the caller's role are returned.

*Constraints:* read-only; k<=5; role filter on sensitivity; chunk text truncated to 700 chars.  *Pinned description hash:* `74fa2e883a9c9bc0`.

```json
{
 "type": "object",
 "properties": {
  "query": {
   "type": "string",
   "minLength": 3,
   "maxLength": 300
  },
  "k": {
   "type": "integer",
   "minimum": 1,
   "maximum": 5,
   "default": 4
  }
 },
 "required": [
  "query"
 ],
 "additionalProperties": false
}
```

### `graph_query`

Read-only Cypher over the knowledge graph (labels/relationships are listed in the schema). Single MATCH...RETURN statement, every node pattern must carry a label, LIMIT <= 50. Labels Person and Diagnosis need role clinician; Variant, Annotation, Sample need analyst.

*Constraints:* read-only (validator + ro_query); one statement; labelled nodes; <=50 rows; label access by role; timeout 2 s.  *Pinned description hash:* `0b1999d9cfbc3c62`.

```json
{
 "type": "object",
 "properties": {
  "cypher": {
   "type": "string",
   "minLength": 8,
   "maxLength": 600
  }
 },
 "required": [
  "cypher"
 ],
 "additionalProperties": false
}
```

### `sql_metric`

Computes a governed metric from the DuckDB warehouse through the semantic layer (never free SQL). Optional grouping by dimensions and equality filters.

*Constraints:* read-only DuckDB views; metric from the semantic layer (7); dimensions validated; <=2 group-by; <=50 rows.  *Pinned description hash:* `13d03bafe4bd4cb8`.

```json
{
 "type": "object",
 "properties": {
  "metric": {
   "type": "string",
   "enum": [
    "call_count",
    "pass_rate",
    "avg_qual",
    "review_min_per_call",
    "pathogenic_share",
    "cpu_hours",
    "avg_daily_backlog"
   ]
  },
  "by": {
   "type": "array",
   "items": {
    "type": "string"
   },
   "maxItems": 2
  },
  "where": {
   "type": "object",
   "additionalProperties": {
    "type": [
     "string",
     "number",
     "array"
    ]
   }
  },
  "limit": {
   "type": "integer",
   "minimum": 1,
   "maximum": 50
  }
 },
 "required": [
  "metric"
 ],
 "additionalProperties": false
}
```

### `get_claims`

Returns the register of alternative claims for a conflict (e.g. different QD/FS/SOR thresholds, Java version) with scope, source, status (active/alternative/superseded) and decision state. Use when sources disagree.

*Constraints:* read-only; no arguments = list of conflicts.  *Pinned description hash:* `47515e3da53466e9`.

```json
{
 "type": "object",
 "properties": {
  "conflict_id": {
   "type": "string",
   "pattern": "^CF-[A-Z]+$"
  },
  "subject": {
   "type": "string",
   "maxLength": 80
  }
 },
 "additionalProperties": false
}
```

### `propose_fact`

Proposes a new fact/claim for the Hub. Does NOT write: the proposal is validated (SHACL + source), classified low/medium/high risk, and queued for human approval; only approved proposals with provenance are ever written.

*Constraints:* no direct write; human approval for risk >= medium; audit log; provenance mandatory.  *Pinned description hash:* `5937b68a72350f26`.

```json
{
 "type": "object",
 "properties": {
  "subject": {
   "type": "string",
   "maxLength": 80
  },
  "predicate": {
   "type": "string",
   "enum": [
    "threshold_value",
    "alias",
    "note",
    "relation"
   ]
  },
  "value": {
   "type": [
    "string",
    "number"
   ]
  },
  "source": {
   "type": "string",
   "maxLength": 200
  },
  "target": {
   "type": "string",
   "maxLength": 80
  }
 },
 "required": [
  "subject",
  "predicate",
  "value",
  "source"
 ],
 "additionalProperties": false
}
```

## 3. Limits (R1 C2)

| Limit | Hardened (default) | Naive (baseline for R4) | Where enforced |
|---|---|---|---|
| tool calls per plan round | 4 | 12 | `agent/graph.py` n_plan |
| plan rounds (replan loop) | 2 | 6 | `agent/graph.py` r_act |
| redrafts after failed verification | 1 | 0 | `agent/graph.py` r_verify |
| total steps (LLM calls + tool calls + verify) | ≤ 14 by construction | unbounded (cap by experiment) | derived |
| tokens per query (estimated, prompt+completion) | 8000 | none | `agent/graph.py` n_draft |
| wall time spent in tools per query | 30 s | none | `agent/graph.py` n_act |
| rows returned by a tool | 50 | 500 | `agent/guards.py` validate_cypher, `tools.py` |
| characters per observation given to the model | 700 | 700 | `agent/tools.py` |
| Cypher timeout | 2 s | none | `agent/tools.py` t_graph_query |

When a limit is hit the agent stops, records the event in the trace (`limit` event) and answers from what it has or with NO_ANSWER; it never retries silently.

## 4. Forbidden actions and human-confirmation rules (R1 C3)

**Forbidden (blocked in code, tested in `tests/test_agent.py`):**

1. Any write/DDL/procedure in the graph through `graph_query` (CREATE, MERGE, DELETE, SET, REMOVE, DROP, CALL, LOAD, FOREACH…): rejected by the validator and executed only with `ro_query`.
2. Free SQL: the warehouse is reachable only through the semantic layer (7 governed metrics, validated dimensions).
3. Reading labels or chunks above the caller's role; returning restricted values (person names, diagnosis ids) to a lower role (output guard).
4. Calling a tool that is not on the allow-list or whose description/schema hash differs from the pinned one (rogue or changed MCP tool).
5. Following instructions that appear inside retrieved data (documents, graph properties, tool descriptions): data is delimited, filtered and never treated as instruction.
6. Revealing the system prompt, the canary marker, keys or secrets; sending data to external URLs; storing secrets or restricted values in memory.
7. Merging a fact into the Hub without validation, provenance and (for risk ≥ medium) a human decision.

**Human confirmation (HITL):**

| Situation | Risk | Rule |
|---|---|---|
| new alias / note about a known entity, source present, SHACL conforms | low | auto-accept into staging, audit-logged, reviewable |
| new *alternative* value for an existing threshold (it can never replace the active claim), or a local/self-reported source | medium | human approval required before anything is written (approved facts go to `proposals/approved_facts.jsonl` with provenance; the agent itself never merges into the Hub) |
| touches restricted data (Person/Diagnosis), implausible value, instruction-like text, unverifiable source, any relation proposal | high | rejected by the validator, nothing is queued |
| validation fails (SHACL violation, no source) | — | rejected, reason returned |

Details, demo and metrics: `docs/hitl.md`.

## 5. Memory (R1 C4)

| Type | Content | Storage | TTL / rule |
|---|---|---|---|
| short-term | state of one run: plan, observations, draft | in memory (LangGraph state) | dropped at the end of the run |
| episodic | role, question (≤200 chars), tools used, status | `logs/memory/episodic.jsonl` | **30 days**, purge job `Memory.purge()`; entries are role-scoped |
| semantic | *approved* facts with provenance (proposal id, approver, source) | `proposals/approved_facts.jsonl` | no expiry, **review after 180 days**; written only by the HITL flow |

Storage rules: never store restricted values (person names, diagnosis ids), secrets or API keys (the write is refused, tested); store no model answers (only status), so that a wrong answer cannot become "memory"; memory only shapes the planner hint (which tools were useful), never evidence. **Status:** implemented (`agent/memory.py`) and unit-tested (TTL expiry, refusal to store restricted values/secrets), but **switched off in all evaluation runs** (`mem=None`) so that prompts, and hence the replay cache, stay fixed; its effect on answer quality was not measured.

## 6. Architecture

LangGraph `StateGraph`: `plan → act → (plan | draft) → verify → (redraft | finalize)`; `verify` checks that every `[id]` is among the observations, that factual answers cite at least one source and that numbers appear in the observations (or are a difference/sum of them); the same tools are exposed through an MCP server (`mcp_server/server.py`, stdio) with a server-side role.
