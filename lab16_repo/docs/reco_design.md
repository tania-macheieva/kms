# Дизайн рекомендаційної системи Hub (ЛР16, результат 1)

**Задача.** Користувачеві Hub (читач / аналітик / клініцист) запропонувати 5 наступних розділів документації, які він іще не читав, з поясненням «чому». Одиниця рекомендації — розділ (chunk) Hub: 680 елементів = 674 чисті розділи з ЛР14 + 6 фікстур-нотаток (позначені `verified=False`, дві з них — навмисно отруєні для перевірки захисту, ЛР12/15).

## 1. Підходи (C1)

| підхід | як працює | код |
|---|---|---|
| **Базова лінія: популярність** | кількість *різних* користувачів, які читали розділ у тренувальному періоді; жодної персоналізації | `reco/models.py::Popularity` |
| **Граф (Cypher-шляхи)** | три запити по графу елементів у FalkorDB: спільна сутність `(a)-[:MENTIONS]->(e)<-[:MENTIONS]-(c)` з вагою idf(e); сусідній розділ `(a)-[:NEXT]-(c)`; той самий документ `(a)-[:IN_DOC]->(d)<-[:IN_DOC]-(c)`. Внесок історії зважується експоненційним згасанням (період напіврозпаду `half_life`). Сутності зв'язані `SAME_AS` із вузлами Gene / AnnotationType графа знань Hub | `GraphReco`, `reco/graphdb.py` |
| **Embeddings kNN** | bge-small (384-вимірні L2-нормовані вектори, ONNX, з ЛР11): оцінка кандидата = зважене середнє top-*m* косинусних подібностей до елементів історії | `KNNReco`, `scripts/build_embeddings.py` |
| **Гібрид** | зважене злиття min-max-нормованих оцінок (`popularity` — через log1p) **або** RRF (k = 60) | `Hybrid` |

Граф елементів: 680 Chunk, 106 Entity, 2235 зв'язків MENTIONS, 641 NEXT, 10 SAME_AS (`ItemGraph.stats()`). Сутності витягує словниковий екстрактор (`reco/entities.py`: інструменти, формати, анотації, геноми, гени з графа Hub, 5 концептуальних фраз); лишаються сутності з частотою у 2…40 % розділів.

## 2. Фільтри якості та доступу (C2)

Фільтри застосовуються **до** ранжування (`reco/models.py::recommend`, `reco/data.py::eligible`), тож заборонений елемент не може потрапити в топ-k:

* **роль / чутливість:** reader бачить `public`; analyst — `public`+`internal`; clinician — +`restricted` (605 / 21 / 54 розділів);
* **верифікація:** `verified=True` (джерело — репозиторій на GitHub або локальний перевірений файл); 6 фікстур — неперевірені;
* **свіжість:** необов'язковий `max_age_days` відносно `AS_OF = 2026-11-08`;
* уже прочитані елементи не рекомендуються.

Демонстрація: `python scripts/filters_demo.py` → `docs/filters_demo.txt`. Ключові рядки: reader із verified_only = 601 кандидат, лише `public`; analyst — 601 public + 18 internal; без фільтра верифікації з'являються неперевірені фікстури (у виводі clinician вони займають місця 391, 588, 633, 670, 675, 678 з 679, тобто рівно фільтр, а не ранжування, їх відсікає); `max_age_days=30` залишає 369 кандидатів; `max_age_days=10` — 0 (порожня видача, а не помилка). Тести: `tests/test_reco.py::test_filters`, `test_recommend_excludes_seen_and_respects_role`, `tests/test_app.py`.

## 3. Гібридне ранжування і параметри (C3)

`score(c) = Σ_k w_k · norm(score_k(c))`, `k ∈ {graph, knn, popularity}`, `norm` — min-max по кандидатах (для популярності — log1p). Альтернатива — RRF: `Σ_k w_k / (60 + rank_k(c))`.

Параметри налаштовуються сітковим пошуком **лише на внутрішньому валідаційному вікні тренувального періоду** (історія — дні < 49, позитиви — дні 49…62; тестові дні ≥ 63 не використовуються), ціль — nDCG@10:

* граф: `ent_w = 1`, `next_w ∈ {1, 3, 6}`, `doc_w ∈ {0, 0.5}`, `half_life ∈ {7, 14, 28}` д;
* kNN: `m ∈ {1, 3, 5}`, `half_life ∈ {7, 14, 28}` д;
* гібрид: `w_graph, w_knn ∈ {0, 0.5, 1, 2}`, `w_pop ∈ {0, 0.1, 0.3}`.

Параметри, що розгортаються в демонстраторі (`reco/config.json`, налаштовані на seed 0): граф `next_w = 1, doc_w = 0.5, half_life = 7`; kNN `m = 3, half_life = 28`; гібрид `w_graph = 0, w_knn = 0.5, w_pop = 0.3`. **Важливо:** у 4 з 5 seed сітка обрала `w_graph = 0` (див. `docs/reco_eval.md`, абляція), тож розгорнутий «гібрид» фактично є kNN + популярність; граф лишається в системі як окремий підхід і як джерело **пояснень** (шлях у графі існує для 97 зі 100 рекомендацій).

## 4. Обмеження (C4)

1. **Синтетичні взаємодії.** Реальних користувачів у Hub ще немає; 64 користувачі й їхні сесії згенеровано (`reco/synth.py`). Метрики відображають здатність відновити *закладену* структуру (теми, перехід до наступного розділу), а не поведінку людей. Це головне обмеження всіх висновків ЛР16.
2. **Малий каталог і словниковий екстрактор сутностей.** 680 розділів, 106 сутностей; сутності, яких немає в словнику, граф не бачить, тож граф слабший за embeddings.
3. **Зміщення до популярного та «бульбашка».** Популярність має найвищу точність у частині seed, але покриття 2 % каталогу; гібрид піднімає покриття до ~20 %, але не гарантує різноманітності; жодного явного штрафу за повтор теми немає.
4. **Лише неявний зворотний зв'язок.** Є тільки «прочитав»; немає негативних сигналів, часу читання, оцінок.
5. **Пояснення — постфактум.** Гібрид ранжує за kNN+популярністю, а пояснення будується з найсильнішого шляху в *графі* між кандидатом і історією (або з kNN-шляху для 3 % випадків). Це правдиве твердження про зв'язок елементів, але не причинна атрибуція рішення моделі.
6. **Cold start лишається слабким для нових документів:** див. `docs/cold_start.md` (hit-rate@10 до 0.07 для нових розділів).
7. **Конфіденційність.** Історія читання — персональні дані; у демонстраторі всі ідентифікатори синтетичні, у зовнішні сервіси (LLM) передаються лише публічні назви розділів і сутності, ключі API в коді відсутні.
