1. Мета, вхідні дані та відхилення від завдання
Мета — виміряти якість сховища знань, виявити й усунути дублікати та суперечності, налаштувати автоматичні перевірки (gate) і оцінити вплив покращення на відповіді RAG-системи з ЛР 11. Генеративна модель працює як експерт (суддя дублікатів, анотатор, рецензент вибірки), усі її рішення позначені рівнями верифікації V1–V4; рішення «людини» ухвалював асистент, схвалення студента (V3) очікується.
Сховище під тестом (baseline): гібридне сховище ЛР 11 — 688 чанків (33 документи: GATK, bcftools, nf-core/sarek, nf-core/raredisease + внутрішні нотатки), граф ЛР 9 (370 вузлів, 757 зв'язків), 4 синтетичні нотатки-фікстури, 34 тести RAG. Версія baseline: baseline-8d41e8b861544136, дата 2026-11-06.
Інструменти: Python 3.13, rapidfuzz, scikit-learn, bge-embeddings (з ЛР 11), pySHACL, rdflib (SPARQL), jsonschema, DuckDB (SQL), pytest, FalkorDB-lite, matplotlib. Усе працює офлайн, без ключів API; відповіді LLM відтворюються з кешу (llm_cache/).
Seed: 14 (вибірка пар, розбиття dev/test, bootstrap/CV); PYTHONHASHSEED=0.
Відхилення від завдання (чесно). (1) Усі «людські» ролі — анотатори, суддя, експерт, арбітр — виконали LLM-субагенти й асистент (одна родина моделей); незалежної людської розмітки немає, тому рівень V3 лишається pending. (2) Фікстури (fx_*) і персона Sofiia — синтетичні з ЛР 9/11, тож частина суперечностей сконструйована; три з восьми (CF-JAVA-TUT, CF-ASM-GRCh37, CF-ASM-GATK) — реальні, з документів. (3) Завдання згадує reasoner для логічних суперечностей; OWL-reasoner у цій роботі не використано — логічне правило (мінімальний вік) перевіряється SHACL-SPARQL обмеженням S14. (4) GitHub-воркфлоу написано, але на GitHub не запускався; gate запускається локально (лог у quality/gate_log.txt). (5) Посеред роботи середовище виконання було скинуто й перша повна спроба ЛР 14 втрачена; усе виконано наново, тож усі числа цього звіту — з другої спроби. (6) Великі мовні моделі недетерміновані (temperature/seed не керуються), тому повторний запуск LLM-кроків може дати інші мітки.

Артефакти: quality/dedup.py, quality/pairs_gold.csv, scripts/{make_pairs,build_pairs_gold,eval_dedup,make_judge_pairs,run_dedup}.py, eval/dedup_eval*.json, quality/merge_log.jsonl, docs/dedup_card.md.
Конвеєр. Нормалізація (без службового першого рядка, заголовків і markdown, нижній регістр) → blocking (інвертований індекс 5-слівних шинглів, пара-кандидат за ≥ 2 спільними шинглами) → порівняння (рядкове: rapidfuzz token_set_ratio та ratio; розріджене: TF-IDF cosine; щільне: bge-embedding cosine; атрибути: той самий документ, хвіст секції, відношення довжин, sensitivity) → рішення.
score = .35*tfidf + .25*emb + .25*fuzz + .15*ratio ; x0.85, якщо len_ratio < 0.5
rule(): різний sensitivity -> не зливати | ідентичний нормалізований текст -> DUP
        score >= th+band -> DUP | |score-th| <= band -> вердикт LLM-судді | інакше -> різні
Blocking лишає 1775 пар із 236 328 можливих (скорочення 99.2%). Для оцінки повноти blocking додано 10 проб (пари з найвищою схожістю embeddings  яких blocking не вибрав): жодна не є дублікатом (0 з 10).

Чому хибне злиття небезпечне. Злиття видаляє чанк із пошуку: якщо «дублікат» насправді містить інший факт (інший поріг, іншу версію, інший конвеєр), знання втрачається, і RAG не зможе його процитувати. Таблиця 7 — Виявлені суперечності, стратегії та виправлення
Стратегії. *Довіра до джерела + рішення власника* (значення): типовим лишається вендорське значення з графа (довіра 1.0), локальне значення зберігається як альтернатива з чітким scope («локальний SOP / протокол клініки»). *Дата/версія* (часові): чинне значення — із поточного README; застаріле позначається superseded з validTo або outdated_flag. *Консенсус у словнику* (терміни): hg19, b37, GRCh37 пов'язано skos:closeMatch, а не exactMatch, бо документ gatk_funco_refdiff прямо каже, що вони не взаємозамінні; два записи ключа sarek — exactMatch із канонічним GATK.GRCh38. *Правило перемагає* (логічні): ребро CT-01 → Sofiia прибрано з активного графа й збережено як DEFERRED_FOR з eligibleAtAge = 18 — дані не втрачено.
Зберігання альтернатив із provenance
Реєстр alternatives.jsonl містить 9 тверджень для 5 суперечностей (значення й часові): поля claim_id, conflict_id, value, status (active | alternative | superseded | outdated_flag), scope, source, origin, confidence, validFrom/validTo, decided_by, decided_at. Аналіз впливу
Вимірюваного приросту якості RAG на 34 тестах немає. Baseline ЛР 11 уже на стелі (faithfulness ≈ 0.99, context recall 0.98), а в контекстах еталонних питань дублів не було: дедуплікація змінила контекст лише одного тесту (T20 — відмова), метрики збіглися в межах шуму (faithfulness 0.9889 → 0.9885 через менше тверджень).
Найбільший ефект — у самому сховищі та в пробнику: усунення суперечностей (8 → 0 відкритих, M03/M04/M07) і дублів (M08 2.0% → 0; 17 → 0 зайвих слотів top-5 із 55). Це обіцяє користь для питань на дубльовані теми, але на цьому тестовому наборі її не виміряно; пробник використовує дослівні уривки чанків і зміщений на користь знаходження.
Реєстр альтернатив не змінив поведінку на конфліктах: у цьому прогоні модель і до, і після відповіла CONFLICT (conflict_detected 1.0). У першій, втраченій спробі на запитання про Java модель дала ANSWER — генерація недетермінована, і один прогін не відокремлює ефект реєстру від шуму; гіпотезу «реєстр покращує конфліктні відповіді» не підтверджено (claims.csv: rejected). Крім того, еталон, що вимагає CONFLICT, суперечить ідеї розв'язаного типового значення — еталон варто переглянути (рішення власника).
Ціна: затримка retrieve p50/p95 майже не змінилась (над-вибірка на 10 чанків), вхід +0.4% токенів.
Невиправлене: M06 (0.64) і M14 (0.96) — попередження; найцінніше, що лишилось, — межі чанків і назви секцій.

Приклад запиту: підказка pair_label_v1 — «для кожної пари {A, B} вибери DUP / RELATED / DISTINCT; суди лише за двома текстами; не шукай схожості; відповідь — JSON зі стислою причиною» (llm_log/prompts/pair_label_v1.txt).
Як перевірено: результати анотаторів — узгодженістю (κ), арбітражем розбіжностей і порівнянням із детермінованою ознакою (точний збіг тексту); код — 9 юніт-тестів + 25 тестів gate; числа — обчислюються скриптами з файлів, а не вводяться вручну; помилки LLM-судді (вигадана відмінність у тексті) виявлено й закрито детермінованим правилом; рішення, що потребують людини, позначено pending.
Відповідальність: студент відповідає за кожне твердження звіту й має пройти рівень V3 (схвалити/відхилити рішення в decisions.csv, переглянути вибірку експерта й спірні пари) до захисту.
8. Відповіді на контрольні питання
1. Які виміри якості ви вимірювали і які пороги встановили? Повнота (M01 = 1.0), валідність (M02 = 1.0, M12 = 1.0), узгодженість (M03 = 0 відкритих суперечностей, M04 = 0, M07 = 1.0, M13 ≥ 0.99), точність (M06 ≥ 0.9, warning), унікальність (M08 ≤ 0 — після дедуплікації не має лишатись жодного дубля; M10 = 1.0), походження (M05 = 1.0: діапазон вихідного тексту чанка міститься в тексті), актуальність (M09 = 1.0: дата ISO і не старша за рік), цілісність графа (M11 = 1.0), доступність/знаходимість (M14 ≥ 0.97, warning). Пороги суворі (1.0 / 0) для детермінованих метрик і м'якші для оцінюваних моделлю або пошуком.
2. Як працює entity resolution і чому хибне злиття небезпечне? Нормалізація → blocking за спільними 5-слівними шинглами → оцінка схожості (рядки, TF-IDF, embeddings, атрибути) → поріг 0.975 (підібраний на dev) → у спірній зоні LLM-суддя з поясненням → злиття з merged_from та unmerge. Хибне злиття видаляє чанк із пошуку разом із його унікальним фактом (інша версія, інший конвеєр), RAG не зможе його процитувати; тому різні sensitivity не зливаються, при сумніві — RELATED, а злиття оборотне.
3. Як ви розв'язали суперечність значень? На прикладі QD: граф каже QD < 2.0, нотатка SOP — QD < 1.5. Вендорське значення лишається типовим (active, довіра 1.0), локальне значення зберігається як alternative зі scope «локальний SOP» і provenance (джерело fx_sop_qd, дата, хто вирішив); у FalkorDB пов'язано ALTERNATIVE_TO. Рішення записано в decisions.csv (хто, коли, чому) зі статусом pending до схвалення власника.
4. Які перевірки виконуються в CI? pySHACL (14 форм, у т.ч. правило мінімального віку S14), SPARQL-інваріанти (3), JSON Schema (3), SQL у DuckDB (3), 14 порогів метрик і тест оборотності злиття; gate розділяє blocking і warning, пише звіт і історію, при blocking-збої виходить із кодом 1.
5. Як якість сховища вплинула на відповіді RAG? На 34 тестах ЛР 11 вимірюваного ефекту немає (baseline на стелі; faithfulness 0.9889 → 0.9885; recall 0.98 → 0.98; conflict_detected 1.0 → 1.0), бо в їхніх контекстах не було дублів; на пробнику дублевих тем зайві слоти top-5 зникли (17/55 → 0/55). Реєстр альтернатив поведінку на конфліктах у цьому прогоні не змінив. Висновок: користь якості видно у метриках сховища й у пробнику, а не в збіглих-на-стелі метриках RAG.
9. Обмеження
Усі анотатори, суддя й «експерт» — LLM однієї родини; їхня згода (κ = 0.97, P/R = 1.0 судді) не є незалежним доказом. Незалежна людська розмітка вибірки не виконувалась.
Лише 17 дублікатів (8 у test): довірчі інтервали дуже широкі (R: 0.38–1.0); комбінована оцінка не краща за TF-IDF.
Більшість об'єднаних кластерів — шаблонний текст nf-core, спільний для sarek і raredisease; для питань про конкретний конвеєр злиття може знеособити відповідь (виправляється unmerge).
Фікстури й персона Sofiia синтетичні; домінні твердження (hg19/b37, Java 17 проти 1.8) частково з пам'яті моделі та з тексту сховища, V3 не пройдено; дата чанків — дата завантаження, не публікації.
Базова лінія RAG на стелі, 34 тести: приріст, меншим за шум, виявити неможливо; генерація недетермінована.
M06 (0.64) і M14 (0.96) нижче порогів; ремонт меж чанків не виконано. Метрика M06 залежить від суворості LLM-експерта (повторний огляд був суворішим).
Воркфлоу GitHub Actions не запускався на GitHub; OWL-reasoner не використано (правило віку — SHACL-SPARQL).
Перша повна спроба ЛР 14 втрачена через скидання середовища; усе виконано наново — числа можуть відрізнятися від тих, що зазначались у проміжних повідомленнях.
