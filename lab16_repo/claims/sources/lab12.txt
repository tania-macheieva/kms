1. Мета, вхідні дані та відхилення від завдання
Мета — спроєктувати зіркову схему, в якій таксономія ЛР5 є виміром, завантажити дані в DuckDB, виконати OLAP-запити (ROLLUP, CUBE, GROUPING SETS, slice/dice, pivot, віконні), описати метрики у семантичному шарі, реалізувати text-to-SQL із захистами та оцінити його, побудувати аналітичну панель.
Бізнес-процес: виклик варіантів у геномній лабораторії (гени спадкового раку). Таксономія — 154 поняття з models/taxonomy_final.csv (ЛР5) з IRI http://example.org/knowledge-hub/biomed/C0xx.
Інструменти: Python 3.13, DuckDB 2.0.0, pandas 3.0.5, sqlglot 30.27, plotly 7.1, rdflib, pytest (43 автотести).
Дані: 20 000 подій-викликів + 2 552 щоденних знімків черги; версія набору 1.0.0  seed 42.
Відхилення від завдання (чесно). (1) Дані синтетичні: реальних подій лабораторії немає; генератор etl/generate.py документовано, розподіли вигадані, тому висновки в інтерпретаціях описують закладені ефекти, а не біологію. (2) Ключа LLM API немає: SQL і питання бізнесу генерував claude-haiku-4-5-20251001 «сліпими» запусками субагентів; відповіді відтворюються з кешу. (3) Набір тестів text-to-SQL складала та сама сесія, що й схему, тож він легкий; «м'яку» метрику визначено після перегляду результатів. (4) Вартість модельна (ціну токенів не звірено з прайсом). (5) «Людський» перегляд виконав LLM-рецензент; рівень V3 — pending. (6) Температура/seed LLM не керуються.
2. Результат 1. Зерно, питання та схема
Артефакти: docs/star_design.md, sql/ddl.sql, docs/star_schema.png. Зерно факту fact_variant_call: один викликаний варіант (call_id) одного зразка, в одному гені, одним конвеєром (версією інструмента) в одну дату. -- question: BQ10 DRILL-DOWN along the taxonomy path (role = variant type): 'Genetic variation' > 'genetic variant' > leaf concept - calls and pass rate at every level -- operation: ROLLUP over the taxonomy hierarchy columns of dim_taxon (top_label > facet_label > label) SELECT t.top_label, t.facet_label, t.label, count(*) AS calls, round(100.0 * sum(f.is_pass) / count(*), 1) AS pass_pct,        grouping(t.top_label) + grouping(t.facet_label) + grouping(t.label) AS rollup_level FROM fact_variant_call f JOIN dim_taxon t ON t.taxon_key = f.variant_type_key GROUP BY ROLLUP (t.top_label, t.facet_label, t.label) ORDER BY rollup_level DESC, calls DESC;

5. Результат 4. Семантичний шар
Артефакти: semantic/metrics.yml, semantic/sl.py, docs/semantic_layer.md. У YAML описано 7 метрик (назва, визначення, формула, одиниця, власник, джерела, адитивність, обмеження, статус, дата перегляду) і 14 вимірів із join-фрагментами та правилом доступності для факту. 8. Відповіді на контрольні питання
Зерно факту — рівень деталізації одного рядка факту (тут: один викликаний варіант одного зразка конвеєром у дату). Його визначають першим, бо воно задає допустимі виміри, адитивність мір і зміст COUNT(*); змішування зерен призводить до подвійного підрахунку.
Таксономія як вимір: dim_taxon (154 поняття, IRI як бізнес-ключ, parent_key, top_label/facet_label) у трьох ролях — тип варіанта, походження, значущість; плюс два посилання з dim_pipeline. Це дає roll-up/drill-down по ієрархії понять (q11, q12, q15) і зв'язок зі SKOS ЛР5 через IRI.
Запит q01: ROLLUP (year, quarter) повертає рядки кварталів, підсумки по роках (g_quarter=1) і загальний підсумок (20 000 викликів, 57.4 % пройшли) за один прохід; grouping() відрізняє підсумкові рядки від NULL-значень. Pivot q07 розкладає значущість за стовпцями для кожного типу варіанта.
Семантичний шар: одне перевірене визначення метрики (формула, одиниця, власник, обмеження), SQL генерується, а не пишеться вручну; різні шляхи дають однакові числа (4/4 перевірки), несумісні зрізи заборонені, словник метрик — основа для text-to-SQL.
Ризики text-to-SQL: хибний, але правдоподібний SQL; ін'єкції; запис/читання файлів; дорогі запити; витік даних. Зменшено: контекст зі схемою та формулами метрик, AST allow-list (20/20 атак блоковано), лише SELECT, примусовий LIMIT, EXPLAIN, read-only без зовнішнього доступу, тайм-аут; виконано небезпечних операторів 0 з 23. Не усунуто: рольовий доступ до рядків, бюджет запитів, незалежна оцінка точності.
9. Обмеження
Дані синтетичні; усі «висновки» — ефекти генератора; хромосоми генів і версії інструментів не звірено з джерелами, дати версій вигадані.
Одна версія таксономії (SCD для неї описано, не виконано); SCD2 застосовано лише до конвеєра.
Тести text-to-SQL легкі, складені тією самою сесією, одна генерація на питання; м'яка метрика визначена після перегляду результатів; вартість модельна.
«Людська» перевірка — LLM-рецензент; claims із V3 — pending.
Немає рольового доступу до даних у text-to-SQL, немає ліміту запитів; семантичний шар — мінімальна власна реалізація (не dbt/Cube).
Температура/seed LLM не керуються; відтворюваність забезпечує кеш відповідей.
